# Wishly

Wishly is a React wishlist application backed by Supabase. Product imports can start from a retailer URL, a name/model search, an image, a barcode, or manual entry. Product metadata and offer results are best-effort: coverage depends on retailer access and configured providers, and Wishly does not claim to search every retailer worldwide.

## Stack

- React 18, TypeScript, Vite, Tailwind, React Router, TanStack Query
- Supabase Auth, PostgreSQL with RLS, and Edge Functions
- Vercel static frontend deployment

## Local setup

1. Install dependencies with `npm install`.
2. Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` for the browser client.
3. Apply migrations `001_initial_schema.sql`, migrations `003` through `028` in order, and `002_seed_data.sql` only if demo content is wanted.
4. Deploy the Edge Functions in `supabase/functions/`: `fetch-product`, `search-products`, `search-image`, `resolve-product`, `refresh-offers`, `refresh-tracked-products`, `check-prices`, and the existing functions.
5. Set `SERPAPI_KEY` in Supabase Edge Function secrets for structured Google Shopping search. Set `OPENROUTER_API_KEY` for the AI assistant and a cited public-web fallback when Shopping has no high-confidence match. `OPENROUTER_MODEL` is optional; the default is `openai/gpt-4o-mini` routed through OpenRouter. Keep all provider keys server-side; never use `VITE_` variables for them.
6. Migration 005 enables `pg_cron` and `pg_net` and creates a private schedule token in Supabase Vault; migration 022 replaces its original hourly alert schedule with a five-minute bounded queue. Migration 006 applies security-advisor fixes; 007 makes the friend visibility helper obey caller RLS. Migrations 014–015 add durable offer-research retries and the 15-minute research schedule. Migration 016 installs atomic daily provider-search budgets used by scheduled and interactive searches. Migrations 017–018 add alert preferences and first-seen offer timestamps; migration 019 stores converted total costs and exchange-rate provenance; migration 020 stores restricted provider usage, search-call counts, latency, result-count, failures, and configurable cost estimates; migration 021 adds durable per-user manual offer-refresh limits; migration 023 makes wishlist imports idempotent; migration 024 preserves same-day availability transitions in price history; migration 025 makes URL import rate limits atomic across Edge Function isolates; migration 026 makes interactive Shopping and image-search limits atomic across Edge Function isolates; migration 027 distinguishes retailer-page-confirmed offers from provider results and migration 028 allows bounded retailer-page verification within the scheduled worker timeout. Scheduled functions validate the Vault token through a service-role-only database function.

Without `SERPAPI_KEY`, URL extraction, internal catalog search, barcode databases, and manual wishlist entry can still run where their providers are reachable. OpenRouter web search may still discover cited retailer pages, but it is not a replacement for structured Shopping prices. UPCitemdb trial access and Open Food Facts have their own coverage and limits.

## Product import and offer behavior

- URL import calls the Supabase `fetch-product` Edge Function, preferring JSON-LD product/offer metadata and falling back to Open Graph tags. Unsupported or blocked pages fall back to manual review.
- Name search combines the internal catalog, UPCitemdb, Open Food Facts, and Google Shopping through SerpAPI when configured. Search results remain candidates for the user to confirm. Interactive Shopping calls use the profile country, language, and preferred currency, an atomic per-user minute limit, and the same durable daily SerpApi budget as scheduled research.
- Image import validates image type and size, then uses the browser's experimental `TextDetector` when available. OCR is not available on every browser; manual entry remains available. OCR prices are unverified observations. Google Lens requests use the profile country and language, atomic per-user minute limits, and the durable daily SerpApi budget.
- Barcode entry validates GTIN check digits and searches the internal catalog, UPCitemdb, and Open Food Facts. Camera scanning depends on browser `BarcodeDetector` support and camera permission.
- Saved items remain available when enrichment or offer search fails. The server-side `refresh-offers` function searches SerpAPI Google Shopping first, then uses OpenRouter's cited web-search results when it finds no high-confidence Shopping match. It preserves retailer URLs and original currencies, rejects conflicting variants, labels title-only/web-snippet results as possible matches, and never treats snippet prices or inferred stock as verified retailer data. Coverage depends on the connected sources; this does not search every retailer worldwide. OpenRouter web search can incur per-search and model-token charges.
- SerpApi delivery text is saved as evidence. Shipping is numeric only for explicit free delivery or a numeric fee expressed in the offer currency; conditional free-shipping thresholds remain unknown. Wishly calculates a delivered total only when shipping and taxes are both known, so current Shopping results generally show item price plus an incomplete-cost label.
- Cross-currency offer ranking uses the user's profile currency and destination country. Exchange rates come from Frankfurter's daily reference-rate API, and Wishly stores the rate, effective date, and source beside original prices. Converted values are estimates for comparison; they do not include card/bank spreads, customs, or checkout-specific conversion fees. See [Frankfurter API documentation](https://frankfurter.dev/).
- User-triggered offer refresh is cached for six hours; the explicit Refresh offers action bypasses that cache and is limited to 10 requests per user per five minutes by an atomic database reservation (migration 021), across Edge Function isolates and concurrent calls. Search uses up to three targeted Google Shopping queries (identifier, brand/model, then title/variant), stopping early when a strong match is found. OpenRouter web search is a bounded fallback when structured Shopping results lack a strong match.
- Saved items are durably eligible for scheduled research through `next_offer_search_at`, so a failed or lost browser request does not remove the item from the queue. Migration 015 schedules one bounded identity per 15-minute worker tick. The worker serves the oldest due items first, checks target-price items every two hours and other items every six hours, and gives alerts and wishlist priority a tie-break preference. It uses OpenRouter web search when Shopping has no strong match, or as the scheduled source when SerpApi is unavailable. Transient provider failures receive exponential retry timestamps; saved offers are retained. The schedule runs only after migrations are applied and at least one provider secret is configured.
- The five-minute alert worker claims at most five due items atomically and inspects at most 12 recent offers per item. Claimed work is leased for crash recovery; follow-up checks run every 30 minutes for target/percentage alerts and every 60 minutes for other enabled criteria. It honors per-item target-price, percentage-drop, any-lower-offer, new-cheaper-retailer, and supported back-in-stock preferences. It requires a fresh high-confidence match and deduplicates notifications by offer, price, and event. Possible title or web-citation matches cannot trigger alerts. Notifications are in-app only; email and push are not configured. Shopping snippets generally have unknown shipping, tax, and stock, so they are not complete delivered-price confirmations. Back-in-stock alerts only run when a source supplies an explicit out-of-stock to in-stock transition. Migration 022 must be applied before deploying the updated worker.
- Daily provider request limits default to `SERPAPI_DAILY_SEARCH_LIMIT=31` and `OPENROUTER_DAILY_REQUEST_LIMIT=8`; both can be set as Supabase Edge Function secrets. The OpenRouter worker still accepts the legacy `OPENROUTER_DAILY_SEARCH_LIMIT` name. Limits are shared atomically across interactive and scheduled searches, including Shopping candidate search and Google Lens. SerpApi's current free plan includes 250 searches/month; set `SERPAPI_DAILY_SEARCH_LIMIT=7` to stay under that quota even across 32 UTC dates (224 reservations). The default cap of 31 is sized for Starter at $25/month for 1,000 searches, allowing at most 992 reservations in a 32-date span. OpenRouter Exa search currently costs $0.007 per request for up to 10 results; Wishly asks for 6, and the 8-call budget with a two-use per-call cap allows at most 16 searches/day, or about $3.58 over a 32-date span, plus model-token charges. Provider prices and plan limits can change; verify them on [SerpApi pricing](https://serpapi.com/pricing) and [OpenRouter web-search pricing](https://openrouter.ai/docs/guides/features/server-tools/web-search) before raising budgets.
- Set `SERPAPI_ESTIMATED_COST_PER_SEARCH_USD` and `OPENROUTER_ESTIMATED_COST_PER_SEARCH_USD` to the account-specific unit costs if you want migration 020 to record estimated spend. These are operator-provided estimates; unset values are stored as unknown rather than zero.

## Commands

- `npm run dev` — local Vite server
- `npm run lint` — ESLint
- `npx tsc --noEmit` — TypeScript check
- `npm run build` — production frontend build
- `supabase start` followed by `supabase test db` — run SQL integration tests, including import idempotency, against the local Supabase database after migrations are applied

## Deployment configuration

Vercel needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. Supabase Edge Functions use the platform-provided Supabase URL, anon key, and service-role key; configure `SERPAPI_KEY` and `OPENROUTER_API_KEY` in the Supabase Dashboard under Edge Functions → Secrets. Optionally set `OPENROUTER_MODEL` there to select another OpenRouter model. The service-role and provider keys must never be added to frontend or Vercel `VITE_` variables.
