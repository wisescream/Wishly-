# Wishly

Wishly is a React wishlist application backed by Supabase. Product imports can start from a retailer URL, a name/model search, an image, a barcode, or manual entry. Product metadata and offer results are best-effort: coverage depends on retailer access and configured providers, and Wishly does not claim to search every retailer worldwide.

## Stack

- React 18, TypeScript, Vite, Tailwind, React Router, TanStack Query
- Supabase Auth, PostgreSQL with RLS, and Edge Functions
- Vercel static frontend deployment

## Local setup

1. Install dependencies with `npm install`.
2. Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` for the browser client.
3. Apply migrations `001_initial_schema.sql`, migrations `003` through `036` in order, and `002_seed_data.sql` only if demo content is wanted.
4. Deploy the Edge Functions in `supabase/functions/`: `fetch-product`, `search-products`, `search-image`, `detect-fashion-items`, `resolve-product`, `refresh-offers`, `refresh-tracked-products`, `check-prices`, and the existing functions.
5. Set `SERPAPI_KEY` in Supabase Edge Function secrets for the existing structured Google Shopping and Google Lens integrations. Google Lens has its own daily app budget (`SERPAPI_IMAGE_SEARCH_DAILY_LIMIT`, default 5). Set `TAVILY_API_KEY` for retailer web discovery; interactive use is enabled by default and can be turned off in the offer-search controls, subject to the daily budget. Optionally set `SEARXNG_URL` to an operator-managed HTTPS SearXNG instance for a free search-lead fallback; SearXNG results are unverified page leads, never saved as offers without a separate product-page inspection. Set `OPENROUTER_API_KEY` for the AI assistant. Interactive OpenRouter web search is enabled for this deployment with `OPENROUTER_ALLOW_PAID_SEARCH=true`; each refresh still requires the user’s expanded-search option and is subject to its daily budget. Scheduled OpenRouter searches are separately disabled by default and require `OPENROUTER_ALLOW_SCHEDULED_SEARCH=true`. `OPENROUTER_MODEL` is optional; the existing web search defaults to `openai/gpt-4o-mini` routed through OpenRouter. Keep all provider keys server-side; never use `VITE_` variables for them.
6. Migration 005 enables `pg_cron` and `pg_net` and creates a private schedule token in Supabase Vault; migration 022 replaces its original hourly alert schedule with a five-minute bounded queue. Migration 006 applies security-advisor fixes; 007 makes the friend visibility helper obey caller RLS. Migrations 014–015 add durable offer-research retries and the 15-minute research schedule. Migration 016 installs atomic daily provider-search budgets used by scheduled and interactive searches. Migrations 017–018 add alert preferences and first-seen offer timestamps; migration 019 stores converted total costs and exchange-rate provenance; migration 020 stores restricted provider usage, search-call counts, latency, result-count, failures, and configurable cost estimates; migration 021 adds durable per-user manual offer-refresh limits; migration 023 makes wishlist imports idempotent; migration 024 preserves same-day availability transitions in price history; migration 025 makes URL import rate limits atomic across Edge Function isolates; migration 026 makes interactive Shopping and image-search limits atomic across Edge Function isolates; migration 027 distinguishes retailer-page-confirmed offers from provider results and migration 028 allows bounded retailer-page verification within the scheduled worker timeout. Scheduled functions validate the Vault token through a service-role-only database function.

Without `SERPAPI_KEY`, URL extraction, internal catalog search, barcode databases, and manual wishlist entry can still run where their providers are reachable. Expanded interactive retailer discovery requires a `TAVILY_API_KEY` and is enabled by default; users can turn it off in the offer-search controls. Scheduled research uses Tavily automatically when its key is configured. Tavily requests have a default daily budget of four and query results are cached for six hours. Set `TAVILY_DAILY_SEARCH_LIMIT` and, if desired, `TAVILY_ESTIMATED_COST_PER_SEARCH_USD` for your account's actual plan. `TAVILY_UNLIMITED_USER_EMAILS` can contain comma-separated auth emails exempt from Wishly's daily Tavily budget, for example test accounts; Tavily's own account limits still apply. OpenRouter search has a separate opt-in flag and daily budget. UPCitemdb trial access and Open Food Facts have their own coverage and limits.

## Product import and offer behavior

- URL import calls the Supabase `fetch-product` Edge Function, preferring JSON-LD product/offer metadata and falling back to Open Graph tags. Unsupported or blocked pages fall back to manual review.
- Name search combines the internal catalog, UPCitemdb, Open Food Facts, and Google Shopping through SerpAPI when configured. Search results remain candidates for the user to confirm. Interactive Shopping calls use the profile country, language, and preferred currency, an atomic per-user minute limit, and the same durable daily SerpApi budget as scheduled research.
- Fashion image import keeps the uploaded photo visible, asks the configured `detect-fashion-items` service for separate normalized item boxes, lets the user select or manually draw one item, and sends only its crop to the existing Google Lens integration. If no detector is configured, manual crop selection remains available. The detection boundary accepts a private HTTPS model service at `FASHION_ITEM_DETECTION_URL`, authenticated with `FASHION_ITEM_DETECTION_TOKEN`; this repository does not include or host a detector model. Google Lens requests use atomic per-user minute limits and the durable daily SerpApi budget.
- Barcode entry validates GTIN check digits and searches the internal catalog, UPCitemdb, and Open Food Facts. Camera scanning depends on browser `BarcodeDetector` support and camera permission.
- Saved items remain available when enrichment or offer search fails. The server-side `refresh-offers` function searches SerpAPI Google Shopping first. The optional expanded search uses Tavily and, when configured, OpenRouter to find public product-page leads; page details are fetched with an SSRF-safe transport, checked against `robots.txt`, and parsed before an offer is saved. Search snippets alone are never treated as price or stock evidence. Discovered retailers start unvalidated; inspection status and evidence are recorded in the retailer directory and discovery history. Search coverage depends on connected providers and retailer access; Wishly does not claim to search the whole web.
- SerpApi delivery text is saved as evidence. Shipping is numeric only for explicit free delivery or a numeric fee expressed in the offer currency; conditional free-shipping thresholds remain unknown. Wishly calculates a delivered total only when shipping and taxes are both known, so current Shopping results generally show item price plus an incomplete-cost label.
- Cross-currency offer ranking uses the user's profile currency and destination country. Exchange rates come from Frankfurter's daily reference-rate API, and Wishly stores the rate, effective date, and source beside original prices. Converted values are estimates for comparison; they do not include card/bank spreads, customs, or checkout-specific conversion fees. See [Frankfurter API documentation](https://frankfurter.dev/).
- User-triggered offer refresh is cached for six hours; the explicit Refresh offers action bypasses that cache and is limited to 10 requests per user per five minutes by an atomic database reservation (migration 021), across Edge Function isolates and concurrent calls. Search uses up to three targeted Google Shopping queries (identifier, brand/model, then title/variant), stopping early when a strong match is found. Expanded search can combine Google Shopping, up to three Tavily queries, OpenRouter web search, and optional SearXNG. It inspects up to six retailer pages per refresh, with slots reserved across providers so one source does not crowd out the others.
- Saved items are durably eligible for scheduled research through `next_offer_search_at`, so a failed or lost browser request does not remove the item from the queue. Migration 015 schedules one bounded identity per 15-minute worker tick. The worker serves the oldest due items first, checks target-price items every two hours and other items every six hours, and gives alerts and wishlist priority a tie-break preference. It uses OpenRouter web search as a scheduled source only when `OPENROUTER_ALLOW_SCHEDULED_SEARCH=true` is explicitly set and Shopping has no strong match, or SerpApi is unavailable. Transient provider failures receive exponential retry timestamps; saved offers are retained. The schedule runs only after migrations are applied and at least one provider secret is configured.
- The five-minute alert worker claims at most five due items atomically and inspects at most 12 recent offers per item. Claimed work is leased for crash recovery; follow-up checks run every 30 minutes for target/percentage alerts and every 60 minutes for other enabled criteria. It honors per-item target-price, percentage-drop, any-lower-offer, new-cheaper-retailer, and supported back-in-stock preferences. It requires a fresh high-confidence match and deduplicates notifications by offer, price, and event. Possible title or web-citation matches cannot trigger alerts. Notifications are in-app only; email and push are not configured. Shopping snippets generally have unknown shipping, tax, and stock, so they are not complete delivered-price confirmations. Back-in-stock alerts only run when a source supplies an explicit out-of-stock to in-stock transition. Migration 022 must be applied before deploying the updated worker.
- Daily provider request limits default to `SERPAPI_DAILY_SEARCH_LIMIT=31`, `OPENROUTER_DAILY_REQUEST_LIMIT=8`, and `TAVILY_DAILY_SEARCH_LIMIT=4`; set account-appropriate values in Supabase Edge Function secrets. The OpenRouter worker accepts the legacy `OPENROUTER_DAILY_SEARCH_LIMIT` name. Limits are shared atomically across provider requests. Provider plans and prices change; configure estimated-cost secrets with current account pricing rather than relying on hardcoded estimates.
- Set `SERPAPI_ESTIMATED_COST_PER_SEARCH_USD` and `OPENROUTER_ESTIMATED_COST_PER_SEARCH_USD` to the account-specific unit costs if you want migration 020 to record estimated spend. These are operator-provided estimates; unset values are stored as unknown rather than zero.

## Commands

- `npm run dev` — local Vite server
- `npm run lint` — ESLint
- `npx tsc --noEmit` — TypeScript check
- `deno check --frozen-lockfile supabase/functions/search-products/index.ts supabase/functions/refresh-offers/index.ts supabase/functions/refresh-tracked-products/index.ts supabase/functions/detect-fashion-items/index.ts` — type-check the deployed retailer search and image-detection Edge Functions using the committed remote-dependency lock
- `npm run build` — production frontend build
- `supabase start` followed by `supabase test db` — run SQL integration tests, including import idempotency, against the local Supabase database after migrations are applied

Migration 030 adds the retailer discovery registry and seeds the first candidate set. Migration 031 extends it to 187 candidate retailer records across Morocco, Europe, Turkey, North America, resale, sportswear, and Asian fashion. All seed records remain unvalidated; Wishly must inspect public product pages before marking a retailer validated. Migration 032 enables budgeted SearXNG search leads for deployments that configure their own HTTPS instance. Migration 033 records SearXNG as a permitted retailer-discovery evidence source. Migration 034 stores conservative seller classifications on offers and adds a seller-type comparison filter; unknown sellers remain explicitly unclassified. Migration 035 stores sanitized provider error categories so search-provider failures can be diagnosed without logging response bodies or secrets. Migration 038 separates the Google Lens image-search daily budget from Google Shopping.
Migration 036 deduplicates retailer records by canonical domain and country while keeping separate regional storefronts and enforcing that identity in Postgres.

## Deployment configuration

Vercel needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. Supabase Edge Functions use the platform-provided Supabase URL, anon key, and service-role key. Configure `SEARXNG_URL` with an HTTPS base URL and optionally set `SEARXNG_DAILY_SEARCH_LIMIT` (default 20) to enable the free web-search fallback. Provider keys belong in Supabase Edge Function secrets. Scheduled OpenRouter usage requires the separate `OPENROUTER_ALLOW_SCHEDULED_SEARCH=true` flag. Configure `FASHION_ITEM_DETECTION_URL` and `FASHION_ITEM_DETECTION_TOKEN` only when you host a compatible detector. The service-role and provider keys must never be added to frontend or Vercel `VITE_` variables. Migration 030 seeds candidate retailers as unvalidated and creates service-role-only search cache and discovery-event tables.
