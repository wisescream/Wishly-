# Product research implementation audit

## Existing flow

URL import calls the authenticated `fetch-product` Edge Function. It parses JSON-LD, Open Graph, and page metadata with redirect, timeout, response-size, DNS, and atomic per-user rate checks (migration 025). The user reviews the extracted fields in the import form, and saving creates a wishlist item, records an initial observation, and queues research. Interactive refresh and the cron worker query Google Shopping through SerpApi, normalize listings into `store_offers`, and write price observations. A separate bounded cron queue evaluates fresh offers for target-price and lower-price notifications.

## Reliability gaps identified

- Search access depends on configured SerpApi and/or OpenRouter credentials; the local environment has no provider credentials, and live requests cannot be verified here.
- Product page extraction now falls back from unusable JSON-LD prices to valid page metadata and withholds price/currency when structured offers and page metadata conflict. The import form asks the user to confirm conflicting values instead of silently pre-filling one.
- A failed retailer-page request previously stopped URL import before product search. The importer now uses only a sanitized final path segment as a provider search hint, preserves the source link, shows candidates for explicit selection, and leaves title and price blank; pages with opaque identifier-only URLs fall back to manual entry.
- Image OCR previously treated a bare `$` as USD and misparsed grouped thousands. It now fills only prices with an explicit supported currency, parses common decimal/grouping formats, and asks the user to choose a currency when a symbol is ambiguous.
- URL and catalog imports now leave unsupported-currency prices blank rather than pairing them with the form's selected currency. Existing provider-only currency codes are displayed as amount plus ISO code instead of being silently formatted as USD.
- JSON-LD `ProductGroup` variants now survive even when the page also declares a selected `Product`; the importer presents listed variant choices and applies their SKU, GTIN, size, color, capacity, image, and only an unambiguous currency-matched price to the editable form.
- Wishlist imports now use an owner-checked, wishlist-locked database RPC. It returns an existing item for the same canonical product/variant, normalized GTIN/variant, or normalized product URL/variant, and preserves its saved values instead of duplicating or overwriting it.
- Interactive and scheduled search previously issued a weak brand-only query when model data was absent. A shared query planner now prioritizes GTIN, then brand/model, then title with the requested variant and omits brand-only requests. Provider transport, matching, normalization, and offer persistence still exist in separate interactive and scheduled flows and can drift. There is no affiliate feed or retailer API configured.
- Search snippets and Shopping results usually do not include tax, checkout price, delivery eligibility, or reliable inventory. Shipping is retained only when the provider explicitly states free delivery or gives a fee in the offer currency. Totals remain unavailable until both shipping and tax are known. Currency normalization now uses dated daily reference rates; it does not represent a bank, card, customs, or checkout exchange rate.
- Search-provider prices were eligible for alerts based on confidence and freshness even though history explicitly stored them as unverified. Migration 027 adds an offer verification flag; alerts now require it, and the scheduled worker independently fetches up to two candidate retailer pages with the DNS-pinned bounded fetch before marking a price confirmed. Only matching, complete page metadata confirms the offer; search results remain visible as unverified leads. Migration 028 raises the scheduled HTTP timeout to 90 seconds for this bounded verification work.
- Retailer page verification previously assigned product-match confidence `1.0` to every accepted identity path. It now reserves perfect confidence for a matching GTIN, scores model/brand and title-based matches separately, and keeps partial title matches below the exact-offer/alert threshold even when the page's displayed price itself was fetched successfully.
- Provider currency attribution now requires explicit currency evidence or a compatible market fallback. Unqualified `$` and `¥` prices are left unpriced when the market cannot identify the currency; shipping amounts use the same ambiguity rule in Edge Functions and UPC catalog imports.
- Product matching uses identifiers, model/title text, and a limited set of variant attributes. It does not perform image similarity or category-specific specification comparison.
- Imported product condition was previously parsed but discarded before the item was saved. Migration 029 stores an explicit target condition, exposes it for editing, keeps new/refurbished/open-box/used/unknown distinct, lowers unconfirmed-condition confidence, and blocks exact-deal ranking and alerts unless the offer condition matches. The migration also preserves condition-aware duplicate imports and extends the durable alert queue payload with the target condition.
- Product URL import validates HTTP(S), credentials, standard ports, private/reserved IPv4/IPv6, DNS A/AAAA answers, and every redirect; DNS lookups are bounded. The fetch path connects to the validated public IP directly, uses the original hostname for TLS verification and the HTTP Host header, and revalidates each redirect target to close the DNS-rebinding gap. Mock transport tests cover pinned requests and redirect validation. Supabase documents native TCP connections in Edge Functions; the exact deployed function still needs a local or live runtime check.
- Price history is stored per item and offer with daily idempotency and ownership checks. The chart separates the original listing from each competitor offer, filters to the selected currency and date range, spaces observations by their actual timestamps, and offers the required time ranges.
- Notifications are in-app only. Per-item target, percentage, lower-price, new-cheaper-retailer, and supported back-in-stock criteria are connected to the scheduled checker. Email and push delivery remain unconfigured, and back-in-stock only works when a provider supplies reliable availability transitions.
- Alert notification records contained the offer URL and variant in JSON payloads, but the Notifications UI showed only clipped body text. Offer alerts now display the variant and price breakdown, a validated direct retailer link, and a link to the tracked item.
- Supabase cron migrations and function configuration are present in source but have not been applied or verified against the live project. Migration 022 changes alert checking from one unbounded hourly scan to a five-minute, five-item atomic claim queue with 30-minute crash leases and 30/60-minute item cadence; each item processes at most 12 recent offers. A Vercel OIDC credential is available and the existing `wishly-` production deployment reports Ready, but this working tree has uncommitted changes and has not been deployed. Read-only live probes returned HTTP 200 from Supabase Auth settings and HTTP 401 from `fetch-product` without a user session; zero-row PostgREST schema probes returned HTTP 400 because `store_offers.is_verified` and `items.next_offer_search_at` are absent, directly confirming migrations 014+ and 027 are not applied to the live database. No Supabase CLI, database credential, service-role key, or authorized test-user session is available, so migrations, genuine offer retrieval, saved history, scheduled monitoring, and alert delivery remain unverified live.
- Manual offer-refresh throttling is now reserved atomically per user in Postgres (10 requests per five-minute window), so the limit persists across Edge Function isolates. Migration 021 must be applied before deploying the updated function; the earlier in-memory limit was only best-effort per isolate.
- The local ignored `deploy.sh` contained a hardcoded GitHub credential and reinitialized the Git repository before force-pushing. The local script now uses Git's configured credential helper and refuses dirty or detached worktrees; the exposed credential still needs to be revoked and rotated by its owner.

## Local implementation status

The local implementation adds retry scheduling, bounded scheduled provider work, a web-search fallback, stricter confidence handling, retailer-page verification, per-listing price-history views, per-item alert criteria, explicit shipping-cost parsing, UPC offer validation, dated currency conversion, shared prioritized search-query planning, query-free provider telemetry, durable per-user rate limits, idempotent wishlist imports, and a bounded durable price-alert queue. Migrations 016–020 add atomic daily provider budgets, alert preferences, first-seen offer timestamps, converted-total provenance, and restricted request/search-count, latency, failure, result, and operator-configured cost metrics; migration 021 adds durable offer-refresh limits; migration 022 adds locked alert-work claims and a bounded cron schedule; migration 023 adds concurrent-safe per-wishlist import deduplication; migration 024 preserves daily stock-state transitions in price history so the back-in-stock worker can require an actual transition; migration 025 makes URL-import limits atomic; migration 026 makes interactive product/image search limits atomic across Edge Function isolates; migration 027 adds verification status; migration 028 extends the bounded scheduled worker timeout; migration 029 persists target condition and returns it to the alert worker. Interactive search functions now reserve from both per-user minute limits and the shared SerpApi daily budget, and record provider outcome metrics. Manual cached/fresh refresh and scheduled refresh now share checked, idempotent price-history writes; offer or history persistence failures log sanitized stages and schedule exponential backoff. Interactive and scheduled search share SerpApi payload parsing, so HTTP 200 API-error responses count as failures rather than empty searches. Database tests cover import/stock-state behavior, condition-aware imports, and durable rate limits; run them with `supabase start` followed by `supabase test db` after migrations are applied. Saving the item and its initial price observation now happens in one database transaction. The 11 import/stock assertions cover initial history creation, duplicate retry idempotency, same-price stock transitions, duplicate imports, and owner isolation; separate tests cover condition-aware imports, URL and interactive search quotas. SQL tests have only been exercised in an isolated PostgreSQL-compatible harness, not with the Supabase CLI. The local changes still require migration application, deployment, and real-provider validation before the product can claim live continuous monitoring.

## Dependency security check

React Router is upgraded to 7.18.4 to include the fixes for the 2026 redirect and SSR hydration advisories; the app uses Declarative Mode, so the SSR hydration issue was not applicable to its current routing setup. `tailwindcss-animate` is now a development dependency because it is only loaded by the Tailwind build config. The production dependency audit reports zero vulnerabilities. The full audit still reports seven development/build dependency findings through Tailwind CSS 3.4.19 and its legacy brace and selector-parser chain. `npm audit fix` cannot resolve these without moving Tailwind to v4, which is a breaking configuration migration; do not claim the complete dependency tree is vulnerability-free.

## Latest local verification

On 2026-10-12, Vitest passed 124 tests across 30 files, `tsc --noEmit` passed, the Vite production build passed, and full ESLint completed with 0 errors and 50 existing warnings. SQL migrations and pgTAP tests were not executed because the environment has no Supabase CLI, Deno, Docker, or PostgreSQL client. The Edge Function entry points were parsed by ESLint; the direct esbuild syntax command could not launch its Termux native binary.
