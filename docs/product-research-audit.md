# Product research implementation audit

## Existing flow

URL import calls the authenticated `fetch-product` Edge Function. It parses JSON-LD, Open Graph, and page metadata with redirect, timeout, response-size, DNS, and atomic per-user rate checks (migration 025). The user reviews the extracted fields in the import form, and saving creates a wishlist item, records an initial observation, and queues research. Interactive refresh and the cron worker query Google Shopping through SerpApi, normalize listings into `store_offers`, and write price observations. A separate bounded cron queue evaluates fresh offers for target-price and lower-price notifications.

## Reliability gaps identified

- Production has a server-side SerpAPI key and OpenRouter key. Live checks show intermittent SerpAPI network timeouts; one recent scheduled request returned Shopping results, while a second reached its timeout. OpenRouter returned HTTP 402 in the latest provider check. Tavily, SearXNG, and a fashion-item detector are not configured, so those discovery and automated image-detection paths are unavailable until their server-side settings are supplied.
- Product page extraction now falls back from unusable JSON-LD prices to valid page metadata and withholds price/currency when structured offers and page metadata conflict. The import form asks the user to confirm conflicting values instead of silently pre-filling one.
- A failed retailer-page request previously stopped URL import before product search. The importer now uses only a sanitized final path segment as a provider search hint, preserves the source link, shows candidates for explicit selection, and leaves title and price blank; pages with opaque identifier-only URLs fall back to manual entry.
- Image-price parsing correctly refuses ambiguous currency symbols and parses common decimal/grouping formats, but it is not OCR. Product photos now use the existing Google Lens visual-search function to produce unverified candidates; image text and prices are not extracted automatically.
- URL and catalog imports now leave unsupported-currency prices blank rather than pairing them with the form's selected currency. Existing provider-only currency codes are displayed as amount plus ISO code instead of being silently formatted as USD.
- JSON-LD `ProductGroup` variants now survive even when the page also declares a selected `Product`; the importer presents listed variant choices and applies their SKU, GTIN, size, color, capacity, image, and only an unambiguous currency-matched price to the editable form.
- The database already had an owner-checked, wishlist-locked, idempotent save RPC, but the active Add Product helper still bypassed it with direct item inserts, browser-side deal searches, and offer writes that defaulted missing prices to zero and condition/availability to new/in-stock. The current local fix routes saves through `save_wishlist_item_once_with_condition`, preserves color/size/capacity/SKU in the saved variant label, records the initial price through the RPC, validates URL and GTIN fields, and leaves offer discovery to the durable scheduled worker. It removes the unused client offer-discovery API that manufactured zero-price retailer search links and could delete existing offers. The production RPC signature, authenticated execute grant, and `next_offer_search_at DEFAULT now()` were checked through the Management API. These frontend/provider changes were deployed to the existing Vercel project `wishly-` on 2026-10-13 07:54 UTC as production deployment `dpl_C3EuFeaagBpJSoLjr5hz1dr9mxdk`, aliased to `wishly-phi.vercel.app`.
- Interactive and scheduled search previously issued a weak brand-only query when model data was absent. A shared query planner now prioritizes GTIN, then brand/model, then title with the requested variant and omits brand-only requests. Provider transport, matching, normalization, and offer persistence still exist in separate interactive and scheduled flows and can drift. There is no affiliate feed or retailer API configured.
- Search snippets and Shopping results usually do not include tax, checkout price, delivery eligibility, or reliable inventory. Shipping is retained only when the provider explicitly states free delivery or gives a fee in the offer currency. Totals remain unavailable until both shipping and tax are known. Currency normalization now uses dated daily reference rates; it does not represent a bank, card, customs, or checkout exchange rate.
- Search-provider prices were eligible for alerts based on confidence and freshness even though history explicitly stored them as unverified. Migration 027 adds an offer verification flag; alerts now require it, and the scheduled worker independently fetches up to two candidate retailer pages with the DNS-pinned bounded fetch before marking a price confirmed. Only matching, complete page metadata confirms the offer; search results remain visible as unverified leads. Migration 028 raises the scheduled HTTP timeout to 90 seconds for this bounded verification work.
- Retailer page verification previously assigned product-match confidence `1.0` to every accepted identity path. It now reserves perfect confidence for a matching GTIN, scores model/brand and title-based matches separately, and keeps partial title matches below the exact-offer/alert threshold even when the page's displayed price itself was fetched successfully.
- Retailer page verification previously checked the requested `variant_label` but did not independently compare color, capacity, gender, or size stated in the saved item title against structured retailer-page attributes. A matching GTIN could therefore overrule a contradictory variant. Verification now checks those explicit attributes and requires an unambiguous page value to agree before accepting the retailer offer; tests cover conflicting color, storage capacity, size, and gender even when the GTIN matches.
- Provider currency attribution now requires explicit currency evidence or a compatible market fallback. Unqualified `$` and `¥` prices are left unpriced when the market cannot identify the currency; shipping amounts use the same ambiguity rule in Edge Functions and UPC catalog imports.
- Product matching uses identifiers, model/title text, and a limited set of variant attributes. It does not perform image similarity or category-specific specification comparison.
- Imported product condition was previously parsed but discarded before the item was saved. Migration 029 stores an explicit target condition, exposes it for editing, keeps new/refurbished/open-box/used/unknown distinct, lowers unconfirmed-condition confidence, and blocks exact-deal ranking and alerts unless the offer condition matches. The migration also preserves condition-aware duplicate imports and extends the durable alert queue payload with the target condition.
- The local product URL import implementation validates HTTP(S), credentials, private/reserved IPv4/IPv6, DNS A/AAAA answers, and every redirect; the fetch path connects to the validated public IP directly and preserves the original hostname for TLS and the Host header. The function authenticates the caller and uses the migration 025 atomic per-user rate limit. Mock transport tests cover pinned requests and redirect validation. This local implementation has not yet been preflighted or deployed, so production URL-import protections are unverified; a signed-in import also needs end-to-end verification.
- Price history and retailer offers had both a broad legacy SELECT policy and a second item-visibility policy. Because permissive PostgreSQL policies are OR-combined, the broad policy exposed rows attached to private wishlist items. Migration 037 removes both broad policies and scopes reads to rows whose item is visible under the existing item RLS rules. A rollback-only production pgTAP run passed all four owner/public visibility assertions (`num_failed() = 0`); no synthetic users or rows remain.
- Price history is stored per item and offer with daily idempotency and ownership checks. The chart separates the original listing from each competitor offer, filters to the selected currency and date range, spaces observations by their actual timestamps, and offers the required time ranges.
- Notifications are in-app only. Per-item target, percentage, lower-price, new-cheaper-retailer, and supported back-in-stock criteria are connected to the scheduled checker. Email and push delivery remain unconfigured, and back-in-stock only works when a provider supplies reliable availability transitions.
- Alert notification records contained the offer URL and variant in JSON payloads, but the Notifications UI showed only clipped body text. Offer alerts now display the variant and price breakdown, a validated direct retailer link, and a link to the tracked item.
- The production database has migrations through 037 applied, and the existing bounded `wishly-refresh-tracked-products` cron is active every 15 minutes. The retailer table contains 186 records: 185 remain discovered and one is temporarily unavailable; none is currently validated. - Manual offer-refresh throttling is now reserved atomically per user in Postgres (10 requests per five-minute window), so the limit persists across Edge Function isolates. Migration 021 must be applied before deploying the updated function; the earlier in-memory limit was only best-effort per isolate.

## Local implementation status

The implementation includes bounded web discovery, metadata extraction, product-page inspection, offer verification, retailer discovery history, price history, price alerts, size-aware filters, and interactive image-item selection with a manual crop fallback. Scheduled and interactive SerpAPI usage is quota-limited and recorded without logging queries. Tavily and OpenRouter calls remain gated by explicit server-side opt-in flags and daily budgets. The Tavily planner now carries product model, variant, SKU, and GTIN into a three-query budget, searching the shopper's market first and then nearby international markets with localized retailer and resale terms. The scheduled worker now probes at most one due retailer sitemap and up to two product pages per tick, respects `robots.txt`, and marks a retailer validated only when a public product page exposes title, price, currency, and image. Product-specific sitemaps can contain ordinary product slugs. Known marketplace domains are classified separately; neither that classification nor a successful probe establishes seller authorization or authenticity. Detection uses a private model-service boundary; this repository does not host a detector model. Full automatic image detection, broad Tavily discovery, and sustained international offer coverage remain unverified until the missing providers are configured and real image/product workflows are exercised.
